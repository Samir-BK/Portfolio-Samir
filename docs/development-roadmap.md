# Development roadmap

Each milestone has its own acceptance checks. Use synthetic fixtures until the owner supplies approved content. Keep the provider and database test environments separate from production. Advance one milestone at a time and record its test results in the change that delivers it.

| Milestone | Deliverable | Acceptance checks | Depends on |
| --- | --- | --- | --- |
| 1. Foundation and design tokens | App Router with strict TypeScript, Tailwind, a base layout, semantic tokens and CI. Pin Node and one package manager. | A clean checkout installs from its lockfile. Lint, type checks and a production build pass. The shell works at 360 px and desktop sizes with visible keyboard focus. | Approval to start implementation |
| 2. Homepage and motion | Original hero, accessible nav, featured project cards, short bio, skills, experience, education and contact links. Use fixture content. | Keyboard users can open and close the mobile menu and regain focus. With reduced motion enabled, content stays visible and decorative transforms are disabled. The page has no horizontal overflow at 360 px. Critical text and links work without client JavaScript. | 1 |
| 3. Projects and writing | Filterable project listing, slug-based project and blog detail pages, safe Markdown rendering, metadata and 404s using a fixture content reader. | Direct URLs load, filtering survives refresh, and unknown slugs return 404. A fixture tests that raw HTML is inert. Public HTML includes the expected title, heading and canonical URL. | 1 |
| 4. Persistent content | PostgreSQL and Prisma with migrations, a seed, published-only reads and publication state. Wire public routes to the database. | On an empty test database, migrate, seed and run the public-route tests. Draft and removed fixtures are absent from lists, detail pages, metadata and sitemap. Published updates appear on the public site. | 2, 3 |
| 5. Protected admin | Managed identity, revocable sessions, project and post editing, publish/unpublish, and audit events. | An authorized owner can save a draft and publish it. Anonymous, revoked and wrong-account sessions cannot read previews or change data. Saving a draft preserves the live version. A concurrent edit yields a conflict. Unpublishing removes public visibility and creates the expected audit entry. | 4, admin provider decision |
| 6. Retrieval and indexing | Public content chunking, database outbox, pgvector ranking and a labeled query set. | An integration test runs migrations including pgvector. Publishing creates searchable chunks, repeating a job creates no duplicates, and a failed job can retry. An old job cannot replace a newer index. An unpublished or stale chunk is excluded even when its embedding row remains. On the initial labeled set, target at least 90% of answerable questions retrieving the expected source in the top five. | 4; use the publication outbox from 5 for end-to-end testing |
| 7. Streaming assistant | Accessible chat UI, cited answers, provider adapter, rate and spend controls, and user-visible fallback. | With a fake provider, tests cover streamed success, cancellation, malformed requests, provider failure, low-confidence questions, invalid citations and rate limits. Run a real-provider staging evaluation for latency, unsupported answers and approved-source citations. Require zero draft disclosures and fabricated citation URLs in the evaluation set. | 6, model and privacy approval |
| 8. Release | Staging and production deployment, public content approval, monitoring, backups and rollback instructions. | Public, admin and chat smoke tests pass on staging. Run keyboard checks and automated accessibility tests on primary routes. Test backup restoration and deploy rollback in staging. Verify HTTPS, session flags, migration status and chat kill switch before publishing. | 1–7 |

The public portfolio can ship after milestone 4 and a public-only pass on the milestone 8 checks. Admin and chat can follow as separate releases. Before milestone 2, collect approved copy and media. Before milestone 5, choose the owner identity. Before milestone 7, agree on provider, monthly cap, retention and acceptable latency. Launch scope can keep contact as a link and treat browser uploads as a later milestone.
